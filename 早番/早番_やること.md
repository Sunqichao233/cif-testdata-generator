## 2. 08:00〜 電話当番と一緒に夜間メールを確認

電話当番（早出）が Outlook を見て、**前日夜間〜当日朝**に障害対応が必要なメールが来ていないかチェックする。

```
電話当番が判断できない
   → 出社済みの早番（＝自分）に声をかけてくる → 一緒に確認
早番でも判断がつかない
   → 顧客担当のPM に確認（不在時は 統括マネージャ）
```

ここは**呼ばれたら答える**立場。自分から Outlook を開く必要はないが、声をかけられたら即対応できるよう席にいること。

切り分けの結果は2つに分かれる：

```
障害        → 下の 3. へ
問い合わせ  → QA表へ。初動フロー（6.）に従う
```

## 3. 「障害」と判断されたら ─ 早番の3タスク

電話当番から以下3点の作業指示が来る。

### 3-1. 過去事例確認

```
利用先一覧シート → 該当顧客の行 → 「シート」列のシート名へジャンプ
                                 → 【過去障害対応】を見る
```

顧客から連携されたメッセージと**同じメッセージが過去に出ていないか**を探す。
各顧客シートには窓口担当者・連絡先・引継ぎ資料・過去QA表・ログの在りか・マニュアルもまとまっている。

### 3-2. 顧客状況確認（電話当番と分担）

- 受電していた場合 → **電話当番が**状況確認する
- 連絡が来ていない場合 → こちらから顧客に連絡して状況確認

**原則、利用先一覧の「保守対象時間」になってから連絡する。**

```
ほぼ全社      9:00 - 17:30
伊予          8:00 - 19:00   ← ここだけ朝8時から
```

ただしメッセージの内容が「完全に止まっている」等なら早めに連絡することもある。
その場合は**必ず早番メンバー or PM に確認してから**かける。

### 3-3. 障害メール第一報を発信 → 保守チャットに転記

**障害受信後15分以内。「拙速を恐れず早いアクションを！」**
代行発信なので、事象と状況が分かる範囲で出してよい。

```
件名：【障害発生連絡】＜ユーザー名：システム名：発生日時：障害ランク＞（○責）

TO ：障害ランクに応じて
       [DL] Accident-A FBD    A：全体停止（障害対策室発動を含む）
       [DL] Accident-B FBD    B：部分プロセス障害（同上）
       [DL] Accident-C FBD    C：再起動可能障害
       [DL] Accident-X FBD    X：不明
Cc ：[DL] ASD ASIDC ；[DL] ASD ASPDC ；[DL] ASD ASPSD1
```

本文6項目：

```
・障害状況     ：現時点の障害状況を簡潔に
・業務影響     ：ユーザ部業務に与える影響
・対応体制     ：管理担当名／作業担当名／究明担当名
・対応状況     ：
・想定原因     ：件名に（自責）／（他責）、不明なら（調査中）
・復旧予測時間 ：
```

- ランク不明なら **X** で出してよい。30分以内に部長以上がランクを判断する運用。
- **経過を更新するときは元メールを赤文字で追記**する。冒頭に一文書いて終わりにしない。メール最後部を見れば常に最新が分かるように。
- 業務影響や顧客目線の進展がない社内向けの更新では、`Accident-xxx` の DL は**外す**（不要な粒度の情報を流さないため）。

テンプレート・サンプル：

```
\\CORE-fs\金融事業本部\AMLGRC事業部\90_部門別\20_ADD2\91_パートナー共有\ノウハウ集\09_障害対応
  └ 【障害発生連絡】＜MEJAR（北陸_北海道銀行）：Oculus-filter 2026_05_29 07_05：障害ランク_X（不明）.msg
  └ 【障害発生連絡】＜ユーザー名：Oculus-XXX 2026XXXX XXXX：障害ランクX（不明）.msg
```

**発信したら、同じ内容を保守チャットにコピペする。** これも 2026/11/09 からの新ルール。
後から出社したメンバーがメールだけでは状況を追えないため。

## 4. 現地調査／リモートが必要なら ─ 申請準備

過去事例を確認した上で、オンサイトでのログ確認・リカバリーが必要と判断されたら、
顧客担当チームPM（or 統括マネージャ）の指示に従って申請を出す。

```
入館者情報を担当者にメールするだけ
    地銀共同 / StellaCube / BeSTACloud / MEJAR / しんきん共同 / 労金 /
    Bizforex / あおぞら / NTTD四国 / TIS / INTEC
申請書を事前に送付
    オリックス / 群馬 / 伊予
```

ログの扱いも顧客で違う：

```
ログ受領 不可（必ずオンサイト、体制図登録者のみ）
    地銀共同 / StellaCube / BeSTACloud
ログ受領 可
    MEJAR / しんきん共同 / 労金
リモート（専用端末）
    群馬 / 伊予（伊予はCAC）
```

ログを送ってもらえる顧客なら、顧客シート記載の**必要なログを取得・送付いただくようメールで依頼**する。

CAC 入室申請・マニュアルは SharePoint の CAC Portal から。

## 5. 以降は顧客担当チームのサブ要員

```
顧客担当チームPM ＋ 統括マネージャ が対応方針を確定
   ↓
主担当    ：顧客担当チーム（プロジェクトメンバー）
サブ要員  ：早番メンバー（＝自分）
   ↓
オンサイト／リモートで 原因調査・リカバリ に同行
```

- 調査方針が固まったら、障害メールに状況を更新（オンサイト対応時刻、リモートアクセス時刻、対応メンバーなど）。これは顧客担当メンバーが発信。
- リカバリ手順の確認・対応は **主担当（顧客担当）＋早番メンバー** で実施。
- 終息メールは顧客担当メンバーが発信。

**原因調査もリカバリも主責は顧客担当チーム。** 自分は協力。

## 6. 問い合わせ（QA）起因だった場合 ─ 初動フロー

今回新設されたフロー。背景は実際に起きた事故：

> フィルタリングの検知漏れを他のQAと同じ扱いで緊急性なく対応し、障害と分かるまで時間を要した。
> マネジメントへのエスカレーションもできていなかった（稼働中のプログラム不具合にはルールが無かった）。

```
QA受領 → 2営業日以内に必ず確認する
   ↓
リスト検知漏れか ──────── Yes → 優先度 = 最高
   │ No                        （調査観点は別紙参照）
   ↓
制裁者関連か ──────────── Yes → 優先度 = 高
   │ No
   ↓
優先度の変更なし
   ↓
QA調査／回答作成（回答作成は2営業日中）
   ↓
再現するか → No → 設定や使い方の調査 → 非障害の可能性 → 再鑑
   │ Yes
   ↓
設定で回避できないか → 回避できる → 非障害
   │ できない
   ↓
障害可能性 → 有識者による再鑑 → 障害確定
   ↓
エスカレーション（社内：A／B／C 障害報知）
   ↓
原因調査 → 顧客宛 障害レター一版発信 → 確定版発信
                                     （全体 5営業日以内）
```

**「検知漏れ」という言葉を見たら、通常のQAキューに並べずに最高優先に上げる。** これが新ルールの核心。

なお、緊急でない調査系のQAは早番ではなく対応メンバーの担当。

## 7. 退勤時 ─ 終了連絡

```
各位

作業を終了します。

作業時間:08:00-17:30

作業内容
・早番
  ＸＸ銀行障害対応
・（プロジェクト名）
  リリース準備　100%
  手順検証　　　30%(遅延）
    ⇒ 手順を確認する環境がなく、検証環境準備に時間を要したため遅延。
       後続タスクの優先度を見直す事でキャッチアップ見込
・社内庶務
```

**遅延したタスクは「％ ＋ 遅延理由 ＋ キャッチアップ方針」をセットで書く。**
